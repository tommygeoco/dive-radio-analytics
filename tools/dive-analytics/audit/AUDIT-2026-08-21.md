## FINDINGS

### CRITICAL

**F-1 · "Expired" broadcasts are alive; plays for E1/E3/E4/E5 are recoverable NOW and the recovery window is being burned**
- What: registry shows 8 X targets latched `broadcastResolved: true` with no `broadcastId` (E1×2, E3×2, E4-ridd, E5×2, plus one E6 extra). These were declared expired/permanently lost. All of them are live:
  - E1: `1AxRnnrOvlrxl` (ridd, 1,022) + `1pKdRRwpkaQJW` (tom, 760)
  - E3: `1nGnRRMEPDkGO` (ridd, 1,429) + `1nGeLLpzNAQKX` (tom, 2,777)
  - E4: `1vJpPPMgdDoJE` (ridd, 1,329) — tom's already tracked (541)
  - E5: `1pKdRDDymlnJW` (ridd, 1,088) + `1AxRnZZeVNzxl` (tom, 958)
- Evidence: broadcast IDs recovered from the announce posts' own t.co redirects (`curl -w '%{redirect_url}'` → `x.com/i/broadcasts/…`); view counts pulled with the pipeline's exact yt-dlp invocation, 2026-08-21 ~16:20 MST.
- Root cause (postlive-track.mjs): `resolveBroadcastId()` (~line 200) only reads the syndication card (`cdn.syndication.twimg.com/tweet-result`). That card disappears/is absent for these posts, so resolution returns null — and the snapshot loop (~line 258) then sets `t.broadcastResolved = true` **even on a null result**, so it is never retried. The tweet's `entities.urls` (already fetched in `fetchXStats`!) contains the broadcast link directly and is never consulted.
- How it corrupts decisions: episode-over-episode X-plays comparisons are built on a roster where 4 of 6 episodes show "unavailable" for a metric that is sitting there retrievable. If broadcasts genuinely expire at ~30 days, E3 data dies ~8/29 — days from now.
- Fix: (a) resolve broadcast IDs from `entities.urls` as first-class fallback (regex `x.com/i/broadcasts/(\w+)` on expanded URLs); (b) never latch `broadcastResolved` on a null/soft result — only after N distinct failed attempts, and record `broadcastResolveFailedAt` instead; (c) **today**, clear the 8 latches / set the recovered IDs above and snapshot — this backfills plays for the whole roster while the window is open.

**F-2 · E4's "541 plays" is a half-episode presented as a whole**
- What: dashboard card shows "X plays: 541" for E4; that is one of two broadcasts (tom only). Ridd's is live at 1,329 → true ≈ 1,870.
- Evidence: registry E4 — ridd target has no broadcastId; history `2026-08-06-…json` last snapshot: ridd plays null, tom 541; live pull above.
- How it corrupts decisions: any read of "E4 underperformed on X" is backwards — with ridd included E4 (1,870) beats E2's 1,801 at comparable completeness. Partial sums shown as totals are worse than no number.
- Fix: when any registered broadcast for an episode lacks plays, render "X plays: 541 (partial — 1 of 2 broadcasts)" or suppress the aggregate. In build-data.mjs, `latest.xPlays` should carry a completeness flag: it currently sums whatever exists (`X_KEYS.some(…) ? reduce(…) : null`, ~line 210) with missing treated as 0.

**F-3 · The original impressions-as-views bug still ships every Monday — in the Slack report and the vault table**
- What: `postlive-track.mjs` `snapshotTotal()` (~line 320) and `renderVault()` (~line 300) sum `views` across all destinations — YT views + X impressions — and label it "total"/"total views". Verified in the 8/17 cron announce: "Data vs. Intuition … **8,139 total**, +112 this week … **All tracked shows: 15,344 total views**" (8,139 = 1,139+913 YT views + 3,863+2,224 impressions). Vault table `Ops/Bones/live-show-analytics.md` Total column: E3 = "21,217" (1,601 YT views + 19,616 impressions).
- How it corrupts decisions: this is the exact unit fraud that broke trust, relabeled on the dashboard but still delivered weekly to the channel where decisions are made. E3 looks like the runaway #1 episode (21,217) when its real video plays are middling.
- Fix: rewrite report/vault rendering to show two totals — "YT views" and "X reach" — and never a combined number. Same for the `Δ day`/"this week" deltas.

### HIGH

**F-4 · Plays failures are silent, and 0 vs unavailable vs expired are not fully distinguishable**
- What: `fetchBroadcastStats()` catches yt-dlp errors, writes one stderr line, and drops the ID (postlive-track.mjs ~line 215). The run still reports "ok". Downstream, plays are simply absent — absent means any of: never had a broadcast / resolution latched / pull failed today / broadcast expired. No status enum, no alert, no distinction. Positive: a failed pull records **absence, not 0** (verified: zero `plays: 0` values in all history), so fabricated zeros are genuinely absent.
- Evidence: only ONE snapshot in the entire history (2026-08-21T23:01Z — today, hours before this audit) contains any plays data. The whole plays feature is one data point old.
- How it corrupts decisions: when E2's broadcasts expire (premiered 7/23; any day now if ~30d holds), the next snapshot silently loses plays, and the dashboard card just stops showing "X plays: 1.8k" — a number Tommy has seen will vanish without explanation. Same for E6 in late September.
- Fix: (a) persist a per-target plays high-water-mark with its timestamp — broadcast plays are cumulative, so "1,801 as of Aug 21 (broadcast expired Sep 22)" is honest and permanent; (b) record per-target status (`ok | pull-failed | expired | none`); (c) a pull that fails for a target that previously had plays must WARN in the run summary, not stderr.

**F-5 · The "fixed" pipeline has never run unattended; discovery failed silently for a month**
- What: cron history shows every daily run 7/21→8/20 snapshotted "2 show(s)" — E3 (7/30), E4 (8/06), E5 (8/13) aired inside that window and were never registered. Three weekly Slack reports (8/3, 8/10, 8/17) shipped covering only E1+E2, all status "ok". Nothing noticed; a human did, a month late. The fix (postlive-discover.mjs + chained cron payload) was installed yesterday/today — and today's 07:25 run **still executed the old payload** (diagnostics: `command ok: "sh" "-lc" "node scripts/restream/postlive-track.mjs snapshot"`). First unattended run of the real chain is tomorrow 07:25.
- Evidence: `openclaw cron runs --id c4bc213f…` (summaries above); job payload now = `discover && snapshot && build && publish`.
- How it corrupts decisions: "all good" is a forecast, not an observation. E7 capture next week depends on code with zero production runs.
- Fix: watch tomorrow's 07:25 run explicitly; wire `audit/validate.mjs` into the Monday payload as a gate (see bottom); keep the roster-count assertion (episodes in data.json vs expected weekly cadence) in the validator.

**F-6 · `&&` chaining makes discovery a single point of failure for the day's snapshot; daily job has no delivery**
- What: payload is `discover && snapshot && build && publish`. If discover exits non-zero (one X API 429/timeline failure at the wrong moment — its per-account try/catch covers lookups but a thrown ytApiKey/other error kills it), snapshot never runs → a full-day gap for every episode. Inversely, snapshot failure blocks publish → dashboard quietly stale. The daily job has **no announce/delivery configured** ("delivery not-requested"), so failures reach no human. Cron history shows real error days already: 5 errored runs 7/25, 4 on 8/11 (both recovered later the same day by retries/manual runs — the 8/18 Anthropic-billing incident did NOT affect these jobs; they're command payloads, zero-model, and 8/18 ran ok).
- Fix: run discover best-effort (`discover; snapshot && build && publish`), and give the daily job an on-failure announce. The staleness tripwire in discover only prints to stdout of a job nobody reads — route it somewhere visible or move it into the validator.

**F-7 · Mixed-unit math still lives in build output: `latest.total`, `cumulativeAllEpisodes`, and the phase-mix insight**
- What: `total(byDest)` with no key filter sums impressions+views. It feeds (a) `episodes[].latest.total` (E3: 21,217 — in data.json and the public repo for anyone to consume), (b) `showTrend.cumulativeAllEpisodes` (15,336 "total"), and (c) the displayed insight "X delivers 80% of first-week views" (`w1x/(w1x+w1yt)` — build-data.mjs platform-phase block), whose denominator is an impressions+views sum. (a) and (b) are currently unrendered by index.html — verified — but they are published poison for any future consumer.
- Fix: delete `latest.total` and `cumulativeAllEpisodes` or split them by unit; rewrite phase-mix as two separate within-unit shares (X week-1 share of X lifetime reach vs YT week-1 share of YT lifetime views) — that comparison is legitimate and answers the same question.

### MEDIUM

**F-8 · Host-split insight is one promoted post wearing a trend costume**
"@designertom … 59% of all-episode X post impressions" — E3's announce (16,541 impressions, the promo outlier) is 54% of tom's lifetime total. The anomaly detector only checks YT views (>2× median), so E3 is not flagged anywhere in current data.json despite being the known promo outlier — the PRD's outlier flag simply doesn't fire on the axis where the outlier lives. Fix: add the same >2× median check on X impressions, and exclude flagged episodes from the host-split aggregate (or report it ex-outlier).

**F-9 · Discovery can still miss or double-register**
- X-only episode (YT upload delayed/absent) is never registered — registration requires a YT anchor; announce posts without a linked known video are skipped ("matches no episode within 3 days").
- Two channels publishing the same episode on different Phoenix dates (11:55pm vs 12:05am upload) → two registry shows, split metrics. Grouping is by exact Phoenix date (postlive-discover.mjs `byDate`).
- The 3-day "mentions dive radio" near-match attaches any host chatter post as an episode destination. Already happened: E6 carries a third X target (2090519715097747965, "Watch it here" → YouTube link) whose impressions inflate E6-tom reach; other episodes have one announce each, so cross-episode reach comparisons are now apples-to-apples-and-a-half.
- Fix: date-group with ±1-day tolerance; require broadcast-card/broadcast-link or explicit video link for X targets (not bare "dive radio" mention); tag non-announce posts as `role: "promo"` and exclude from per-account reach comparisons.

**F-10 · E2 slipped under the late-reg threshold**
E2's first snapshot is 4.3 days post-premiere (7/27 vs 7/23) — under the 5-day `PARTIAL_THRESHOLD_DAYS`, so E2 counts as "full history" in every baseline despite missing days 0–4 (the hottest X window; its first tracked X-ridd number is already 3,580). Week-1 velocity (cumulative at day 7) is fine, but the phase-mix "first week" X share for E2 is built from a day-4.3 entry point. With n=2 full-history episodes, half the baseline has a soft foundation. Fix: either mark E2 `partialHistory` manually or add a `firstSnapshotAgeDays` field and let math degrade gracefully instead of binary include/exclude.

**F-11 · Same-broadcast dedupe attributes plays to one account arbitrarily**
`seenBroadcasts` (snapshot loop) prevents double-counting when both hosts announce the same broadcast, but the plays land entirely on whichever target iterates first — per-account plays splits would be silently wrong the first time the hosts share one broadcast. Not hit yet (all episodes so far have distinct per-host broadcasts). Fix: attribute shared broadcasts to a synthetic `x:shared` key or split explicitly.

**F-12 · Weekly `--all` mode won't survive the roster growing**
`snapshot --all` and `report --all` walk every episode forever. `fetchBroadcastStats` is serial yt-dlp with a 90s timeout per broadcast; expired broadcasts burn the full timeout. At 50 episodes ≈ 100 broadcasts, worst case >2 hours vs the job's `timeoutSeconds: 600` — the Monday job will start timing out somewhere around episode 25–40, and because of F-6's chaining, that kills the report too. Fix: skip yt-dlp for targets already marked expired/high-watermarked; parallelize (4-way) with a short timeout; cap `--all` broadcast pulls to the last 45 days.

### LOW

**F-13 · data.json embeds every raw snapshot forever** — ~30KB/episode/month; at 50 episodes ≥ 5MB of data.js parsed in-browser on a page that renders all series (CARD_CAP collapses cards, not datasets). Fix eventually: downsample snapshots older than 60 days to weekly in the export.
**F-14 · Vault Δ-day clamps negatives** — `+${num(Math.max(r.delta, 0))}` renders any decrease as "+0", masking corrections. Minor, but it's a small fabrication of the same family as the big ones.
**F-15 · YT view counts dip by 1 occasionally** (six single-digit dips in history — YouTube-side corrections). Harmless; validator warns, doesn't fail. Worth knowing so nobody chases ghosts.
**F-16 · Week boundaries** — `mondayNoonAtOrBefore` hardcodes UTC-7; correct for Phoenix (no DST) year-round, verified boundary math on 8/03–8/17 series. No DST bug *for this timezone*; the hardcode becomes wrong the day the show anchors anywhere else.
